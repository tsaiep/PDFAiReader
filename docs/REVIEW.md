整體來說這份計劃書寫得不錯：「閱讀器優先」的方向對，OCR／版面分析／翻譯三層分開也做得好，快取的失效規則和風險章節也比一般計劃書完整。值得優化的地方集中在三點：**最大的技術風險被排得太晚**、**幾個關鍵的架構決策沒寫**、**驗收標準不夠具體**。下面依重要性排列。

---

## 一、高優先：建議在動工前就改

### 1. 先加一個 Phase 0：Codex CLI 可行性測試
整個翻譯功能都靠 `codex exec`，但它本來是寫程式用的 Agent，不是翻譯 API。計劃書 9.3 也提到要「開發初期實測」，但實際上被排在 Phase 3。建議先花 1–2 天做一個獨立的小測試，量這幾件事：
- 每次呼叫的啟動時間，以及翻譯一頁從送出到拿到結果要多久
- 一頁大概用掉多少額度，連續翻 50 頁會不會碰到使用上限
- `--output-schema` 或 `--json` 能不能穩定回傳合法 JSON
- CLI 到底能不能列出可用模型。如果不能，3.2 的「從 CLI 產生模型清單」就要改成「手動輸入加上測試驗證」
- **用 ChatGPT 訂閱大量翻譯整本書，是否符合使用條款**

測試結果會直接決定批次大小、預翻頁數 N 的預設值，甚至決定 Codex 適不適合當主要引擎。

### 2. 翻譯引擎的抽象介面提前到 Phase 3
Phase 6 才列入多引擎（Ollama／API），但介面應該第一天就定好，例如 `protocol TranslationEngine`，Codex 只是其中一個實作。這樣做也方便寫測試：可以做一個 Mock Engine，單元測試就不用真的呼叫 CLI。

### 3. 補上「App Sandbox 和發佈方式」的決策
這點沒寫但影響很大：
- 開了 App Sandbox 的 App 很難去執行外部的 `codex` 程式，所以多半只能**不開 Sandbox、不上 Mac App Store**，改用 Developer ID 簽章加公證來發佈。
- 從 Finder 啟動的 GUI App **拿不到 shell 的 PATH**。如果 codex 裝在 `/opt/homebrew/bin` 或 nvm 底下會找不到，需要自動偵測路徑，再讓使用者能手動指定。
- 安全性方面：OCR 文字要從 stdin 或暫存檔送進去，不要放在命令列參數；CLI 的工作目錄設成一個空的暫存資料夾，再加上 `--sandbox read-only`。

### 4. OCR 也需要排程，而且要和翻譯串起來
第四章只排程翻譯，但實際流程是「OCR → 版面分析 → 翻譯」，翻譯任務必須等 OCR 做完。建議改成一條統一的處理管線，任務之間有依賴關係，OCR 也照可見頁、預讀頁、背景的順序排優先級。否則跳到第 200 頁時，翻譯排到了，OCR 卻還在背景慢慢從第 1 頁做起。

### 5. 選取文字的翻譯需要獨立通道
並行數預設是 1，所以使用者選一段文字，可能要等整頁的批次跑完，「最高優先」等於失效。建議分兩條通道：**互動通道（選取文字）保留 1 個名額**，背景通道（頁面、預翻、整書）另外 1 個。

## 二、中優先：規格上的缺漏

| 問題 | 建議 |
|---|---|
| **優先級名稱撞名**：功能表用 P0–P2，任務排程也用 P0–P3，容易混淆 | 任務優先級改用 `interactive / visible / prefetch / background` |
| **OCR 文字的選取和搜尋**被列為 P0，但 PDFKit 不會自動讓你的 OCR 結果變成可選取的文字 | 寫明要自己做一層透明的選取 overlay，這是不小的工程量，估時要反映出來 |
| **座標轉換**沒提 | Vision 回傳的是正規化座標、原點在左下角，PDFKit 還有頁面旋轉和 cropBox 要處理。座標一律存成「頁面空間」，並寫測試 |
| **文件識別碼**：整個檔案算雜湊，遇到 500MB 的 PDF 很慢 | 用快速指紋（檔案大小 + 頭尾各 1MB 的雜湊），再搭配 macOS 的 bookmark 追蹤搬移過的檔案 |
| **隱私說明前後不一致**：原則寫「不上傳書頁」，但文字其實會送到 OpenAI | 明確說明 OCR 文字會送出翻譯，第一次使用時請使用者確認 |
| **來源語言和目標語言**：Prompt 寫死繁體中文，設定畫面卻有「目標語言」 | 二選一：v1 只做繁體中文，或把 Prompt 模板化 |
| **術語表從哪裡來**沒寫 | v1 先做手動維護；自動抽取術語可以放到後續版本 |
| **翻譯結果驗證**的規則沒寫細 | 檢查回傳的區塊 ID 和送出的完全一致（不能缺、不能多、不能重複），部分失敗時只重試缺少的區塊 |
| **預翻譯方向**：往回捲動或右至左閱讀時，「後續 N 頁」是指哪幾頁？ | 依照閱讀方向和最近的翻頁方向決定，加上大約 300–500ms 的防抖（debounce） |
| **深色模式完全不反相** | 保留預設不反相，但可以提供一個「夜間模式」開關給純文字頁使用 |

## 三、階段安排和驗收標準

- **大型文件效能不要拖到 Phase 5。** 300 頁以上掃描 PDF 的記憶體和翻頁流暢度，應該是 Phase 1 的驗收條件，否則後面很難回頭修。
- **Phase 2 的版面分析範圍要收斂。** v1 只要做到單欄和標準雙欄；藝術書的不規則排版另外標成後續版本，不然這一階段很容易做不完。
- **驗收標準要量化。** 例如：
  - 300 頁 PDF 開啟後 2 秒內顯示第一頁
  - OCR 進行中，翻頁仍維持 60fps，記憶體不超過某個上限
  - 單頁 OCR 在 Apple Silicon 上少於 N 秒
  - 雙欄頁面的閱讀順序在測試集上正確率達 X%

  像「合理的閱讀順序」這類寫法，交給 Codex 開發時沒辦法判斷是否完成。
- **測試資料集要固定下來。** 第十章列的 6 類文件，實際放進 repo（或註明來源），每類搭配人工標註的正確結果，作為 OCR 和版面分析的回歸測試。

## 四、技術選型可以寫得更具體

- SQLite 建議直接指定 **GRDB.swift**，它內建 migration、並行存取和觀察資料變化。
- 註明使用 **Swift 6 嚴格並行檢查**。另外要注意 `PDFDocument` 不保證執行緒安全，背景渲染或 OCR 應該使用獨立的文件實例。
- 既然是用 Codex 開發，交付物可以加一份 **AGENTS.md**，寫明模組邊界、程式風格和測試指令。每個階段再拆成小任務，每個任務都附上驗收條件，AI 產出的程式碼品質會穩定很多。

---

**總結：** 最值得改的三件事是：**加 Phase 0 驗證 Codex CLI**、**OCR 和翻譯共用一套排程**、**把 App Sandbox／PATH／發佈方式的決策寫進文件**。其他項目屬於補規格，可以邊做邊改。
